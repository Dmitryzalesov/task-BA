# 1.1. Процесс работы аналитика и взаимодействие с командой разработки

## 1. Получение и первичный анализ задачи

Аналитик получает от Заказчика описание необходимости вернуть закупочную процедуру на этап «Подача заявок», а также технические материалы:

- описание бизнес-требования;
- пример XML-сообщения;
- информацию об интеграции SAP с ЭТП.

На первом этапе аналитик определяет:

- какую бизнес-проблему необходимо решить;
- какие пользователи и системы участвуют в процессе;
- какие процессы и сущности затрагиваются;
- какие изменения ожидаются от системы;
- какие требования являются функциональными, а какие относятся к интеграции.

---

## 2. Анализ бизнес-процесса

Аналитик восстанавливает процесс проведения закупочной процедуры и определяет место возврата процедуры в общем жизненном цикле.

В рамках данной задачи необходимо определить:

1. из какого состояния процедура может быть возвращена;
2. в какой статус она переводится;
3. какие заявки существуют на момент возврата;
4. что происходит с ранее поданными заявками;
5. какие действия доступны Заказчику;
6. какие действия доступны Поставщику;
7. как заявка участвует в повторном вскрытии.

Отдельно анализируются сценарии:

- заявка оставлена без изменений;
- заявка изменена и повторно подписана ЭП;
- заявка отозвана.

---

## 3. Анализ интеграции

Аналитик изучает XML-сообщение, через которое SAP передает изменения процедуры на ЭТП.

Необходимо определить:

- формат сообщения;
- namespace;
- идентификатор процедуры;
- идентификатор сообщения;
- расположение признака возврата `Is_Returned`;
- источник даты окончания подачи заявок;
- правила обработки сообщения.

При сопоставлении бизнес-описания с предоставленным XML выявляются расхождения:

- в описании указан один namespace, а в XML — другой;
- в описании присутствует `Is_Returned`, но в предоставленном примере этот тег отсутствует;
- структура XML из описания отличается от структуры предоставленного примера.

Аналитик не должен самостоятельно выбирать один из вариантов без подтверждения. Расхождения фиксируются как открытые вопросы и выносятся на согласование.

---

## 4. Формирование требований

На основании анализа аналитик формирует функциональные и системные требования.

В требования включаются:

- изменение статуса процедуры;
- изменение доступности ранее поданных заявок;
- возможность Поставщика изменить или отозвать заявку;
- правила определения действующей версии заявки;
- правила формирования повторного вскрытия;
- отправка уведомлений;
- обработка ошибок;
- защита от повторной обработки сообщения.

Требования формулируются таким образом, чтобы они были однозначно проверяемы командой разработки и тестирования.

---

## 5. Выявление открытых вопросов и рисков

В процессе анализа аналитик фиксирует информацию, которой недостаточно для однозначной реализации.

Например:

- какие статусы процедуры допускают возврат;
- как определяется новая дата окончания подачи заявок;
- как хранится история изменения заявки;
- какой статус получает отозванная заявка;
- как формируется пакет повторного вскрытия;
- используется ли `MessageId` для идемпотентности;
- какой XML-контракт является актуальным.

До начала разработки критичные вопросы должны быть согласованы с Заказчиком или владельцем соответствующей системы.

---

## 6. Подготовка постановки для разработки

После анализа аналитик преобразует бизнес-требование в технически понятную постановку.

Постановка содержит:

- контекст задачи;
- требуемые изменения;
- интеграционные требования;
- сценарии работы с заявками;
- требования к уведомлениям;
- обработку ошибок;
- Acceptance Criteria;
- открытые вопросы.

Результатом является документ `03-development-task.md`.

---

## 7. Передача задачи команде разработки

Перед передачей задачи аналитик проводит проверку постановки:

- все требования имеют однозначную формулировку;
- отсутствуют противоречия между разделами;
- определены основные сценарии;
- указаны интеграционные изменения;
- критичные открытые вопросы вынесены отдельно;
- для основных требований сформированы критерии приемки.

После этого задача передается команде разработки.

---

## 8. Взаимодействие с командой разработки

После передачи задачи аналитик участвует в уточнении требований.

### До начала разработки

Аналитик совместно с разработчиками:

- разбирает интеграционный контракт;
- уточняет спорные места;
- отвечает на вопросы по бизнес-логике;
- при необходимости уточняет требования у Заказчика;
- фиксирует согласованные изменения в постановке.

### Во время разработки

Аналитик:

- отвечает на возникающие вопросы;
- контролирует соответствие реализации требованиям;
- уточняет бизнес-сценарии;
- актуализирует документацию при изменении требований.

При обнаружении нового сценария или ограничения аналитик не принимает решение самостоятельно, если оно влияет на бизнес-логику. Изменение согласуется с заинтересованными сторонами.

### После завершения разработки

Аналитик участвует в проверке результата по Acceptance Criteria:

1. проверяется возврат процедуры;
2. проверяется изменение видимости заявок;
3. проверяются сценарии работы Поставщика;
4. проверяется формирование повторного вскрытия;
5. проверяется отправка уведомлений;
6. проверяется обработка ошибок;
7. проверяется защита от повторной обработки сообщения.

Если реализация соответствует согласованным требованиям, задача принимается.

---

## 9. Схема взаимодействия

```text
Заказчик
   │
   │ Бизнес-требование
   ▼
Аналитик
   │
   ├── Анализ бизнес-процесса
   ├── Анализ XML и интеграции
   ├── Выявление сценариев
   ├── Выявление противоречий
   ├── Формирование требований
   └── Формирование Acceptance Criteria
   │
   │ Постановка задачи
   ▼
Команда разработки
   │
   ├── Уточнение технических вопросов
   ├── Реализация
   └── Обратная связь аналитику
   │
   ▼
Аналитик
   │
   ├── Уточнение требований
   ├── Согласование изменений
   └── Проверка по Acceptance Criteria
   │
   ▼
Результат
```
---
## 10. Результаты работы аналитика
| Артефакт | Назначение |
|---|---|
| Анализ требований | Понимание бизнес-процесса и выявление проблемных мест |
| Описание сценариев | Формализация поведения системы |
| Анализ XML | Определение интеграционных требований и расхождений |
| Открытые вопросы | Фиксация информации, требующей согласования |
| Постановка задачи | Передача требований команде разработки |
| Acceptance Criteria | Проверка соответствия реализации требованиям |
